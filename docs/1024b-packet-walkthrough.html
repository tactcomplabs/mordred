How a 1024 B packet crosses two endpoints through a Mordred router over UCIe

Endpoint A and Endpoint B each run mordred.mordredNicPC; a single mordred.mordred_router sits between them; every hop is a prydwen.uciePhysChannel die-to-die link. Every number below comes from the SST_ELI_DOCUMENT_PARAMS defaults and the serialization math in ucieAdapterBase.h — nothing here is tuned.

01 — TOPOLOGY

The physical path

Each UCIe link is its own uciePhysChannel instance loaded as the port_iface of a mordredNicPC (endpoints) or rtrPortControlPC (router). The router needs one more port than it has local endpoints, so a 2-endpoint router is configured with num_local_ports=2, num_ports=3 — the third port stays unconnected.

02 — PACKET ANATOMY

What "1024 bytes" turns into on the wire

mordredNicPC::transportSendFlit() hands every Mordred flit to the UCIe channel with packet_size_bits=0 — each one travels as its own atomic, single-fragment UCIe message (uciePhysChannel.cc:47). So the packet's fate is decided entirely by Mordred's own flit width, not UCIe's fragmentation logic.

1024 B request → calcNumFlits(8192 b ÷ 32 b) = 256 Mordred flits

4 bytes of real payload riding inside a 256-byte UCIe format-5 flit — because every one of the 256 Mordred flits consumes its own full wire slot (see callout below).

03 — TIMING

Sequence diagram: HEAD → 254 × BODY → TAIL

Five lifelines: the two NICs, the two UCIe links, and the router's crossbar. Every flit pays 4 ns to serialize (ser_delay_ps, 256 B ÷ 512 Gb/s) plus 2 ns to propagate (link_latency) on each of the two hops. The router adds a few extra nanoseconds once, for VC/switch allocation on the HEAD flit — mordred/README.md lists router pipeline depth as fixed and not yet configurable, so this is an emergent cost of the state machine, not a documented constant. After HEAD wins its VC and crossbar slot, the router holds that path for the rest of the packet (§ "packet-based switching"), so BODY/TAIL just ride the link's own 4 ns cadence.

04 — WHAT THE DEFAULTS ACTUALLY DO

The flit-size mismatch is the whole story

Efficiency at default settings ≈ 1.6%

Mordred's default flit_size is 32 bits (4 B). UCIe's default flit_format 5 wire flit is 256 B. Because RtrPortControlPC/MordredNicPC send every Mordred flit as its own independent UCIe message (packet_size_bits=0), each 4-byte flit burns an entire 256-byte physical slot. That ratio, not the router's clock or the link's propagation delay, is what turns a 1024 B packet into a ~1 µs transit.

num_flits = ceil(1024 B×8 / 32 b) = 256 flits
ser_delay = ceil(256 B×8 / (1×16×32 Gb/s)×1000) = 4 ns/flit
efficiency = 4 B ÷ 256 B = 1.56% payload/wire
latency ≈ 256 × 4 ns + 2×(4 ns + 2 ns) + router alloc ≈ ~1.03 µs

This isn't a bug — it's the documented default pairing. Raising flit_size to match UCIe's payload width (e.g. matching the 240 B usable payload of format 5), or dropping to flit_format 2 (68 B wire), collapses this overhead; the test configs under mordred/tests/*_uciePhysChannel*.py already do this (e.g. flit_size="16b" paired with a real router-to-router link). The numbers above are what you get if you change nothing.
