01 — TOPOLOGY

The physical path

Each UCIe link is its own uciePhysChannel instance loaded as the port_iface of a mordredNicPC (endpoints) or rtrPortControlPC (router). The router needs one more port than it has local endpoints, so a 2-endpoint router is configured with num_local_ports=2, num_ports=3 — the third port stays unconnected. Numbers below are measured from a real run of this exact topology (message_size=1024B, flit_size=32b), not hand-calculated.

02 — BUFFER ARCHITECTURE

Where the per-(vn, vc) buffers actually live

Zooming into one router port's outbound side (the direction transportSendFlit() runs). Two components own real, independent per-VC buffers today; one used to lose the VC dimension entirely at the handoff between them — that gap is what the widening fix in §05 closes.

03 — PACKET ANATOMY

What "1024 bytes" turns into on the wire, before and after

calcNumFlits(8192 b ÷ 32 b) = 256 Mordred flits is unchanged by the fix — the packet is still logically 256 flits (confirmed by the real run's average_packet_size = 256.000000). What changed is how many of those flits each cost their own physical UCIe wire transfer.

transportSendFlit() used to hand every Mordred flit to the UCIe channel with packet_size_bits=0, so each one — including all 254 BODY flits — became its own atomic, single-fragment wire message: 256 physical UCIe flits for one packet, 4 bytes of real payload in each 256-byte wire slot.

After: HEAD only
→ 5 wire flits

Now only the HEAD triggers a real wire transfer — carrying the true packet size, it fragments into ceil(1024 B ÷ 240 B) = 5 physical UCIe flits, each one packed with real payload (240 of 256 bytes). BODY/TAIL become free no-ops on the wire; the far side's FlitFactory resynthesizes all 256 Mordred flits from those 5 fragments. 256 → 5 physical wire flits for the same packet.

05 — WHAT WAS WRONG, WHAT IT TOOK TO FIX, AND WHAT IT COST

Three bugs, one fix, one honest caveat

The original finding — efficiency at defaults ≈ 1.6%

Mordred's default flit_size is 32 bits (4 B); UCIe's default flit_format 5 wire flit is 256 B. RtrPortControlPC and MordredNicPC sent every Mordred flit as its own independent UCIe message (packet_size_bits=0) — including all 254 BODY flits of a packet that should never have needed their own wire transfer — so each 4-byte flit burned an entire 256-byte physical slot: 256 wire flits for one packet, ~1.6% payload efficiency.

Fixing it took three changes, not one

1. Coalesce on HEAD (RtrPortControlPC.h, MordredNicPC.h) — only the HEAD flit now triggers a real wire transfer, carrying the true packet size so UCIePhysChannel::send() fragments it properly; BODY/TAIL become free no-ops, reconstructed on the far side by the existing (previously unused) FlitFactory.

2. Drain fragments back-to-back (prydwen/src/ucie/ucieAdapterBase.h, trySend()) — the multi-fragment path had never been exercised before, and only dispatched one fragment per credit round-trip; without this fix, coalescing's benefit would have been mostly cancelled out by round-trip-paced draining instead of back-to-back serialization.

3. Widen UCIe addressing to (vn, vc) (RtrPortControlPC::extVn(), symmetric widening in MordredNicPC) — coalescing a whole packet into one uninterruptible wire burst broke VC-based deadlock avoidance on wraparound topologies (confirmed: a 5×5 torus deadlocked after the first two fixes landed). Fixing this required giving every Mordred VC its own independent UCIe wire queue and credit pool, since UCIe's addressing had only ever kept track of vn.

The honest caveat — this is a wire-efficiency fix, not a router-throughput fix

A follow-on discovery while chasing the torus deadlock: coalescing also raised the per-flit credit-turnaround latency at every hop (RtrPortControlPC.h's pendingFlits_ drip queue still drains bulk-delivered flits one per router cycle, so a large packet's credit round trip now takes O(M) cycles longer than before — see the doc comment there for the full mechanism). Ports need real output_buf_size headroom to absorb that, not the bare 1-flit minimum that sufficed under the old model.

And under heavy concurrent load, the improvement above doesn't show up: a 9-router mesh saturated with all-to-all 1024 B traffic completed in 94.752 µs before the fix and 94.897 µs after — statistically the same. Coalescing removes wire overhead; it doesn't change the router's one-flit-per-cycle crossbar throughput, and under heavy contention that crossbar rate, not the wire, is what limits completion time. The win is real for latency-sensitive, lightly-loaded traffic — the isolated single-packet measurement above — not for peak aggregate throughput at saturation.
